# Пояснення (частина 2): маршрутизація на декораторах і валідація

Розбір частини 2 «своїми словами»: у чому суть, які рішення прийнято і чому саме
так. README описує *як користуватись*; тут — *чому воно так влаштоване*. Про
контейнер (частина 1) — окремий файл `EXPLANATION.md`.

---

## 1. У чому суть завдання

Частина 1 навчила контейнер **створювати обʼєкти** з метаданих. Частина 2 робить
наступний крок: той самий підхід — «декоратор пише метадані, рушій їх читає» —
застосовуємо до **HTTP**. Ми хочемо писати так:

```ts
@Controller('users')
class UserController {
  constructor(private users: UserService) {}      // сервіс дає контейнер

  @Get(':id')
  getOne(@Param('id') id: string) { ... }          // id підставляється сам

  @Post()
  create(@Body() dto: CreateUserDto) { ... }        // тіло вже валідне і типізоване
}
```

…і ніде не чіпати `req`/`res` вручну. Питання, на яке відповідає ДЗ: **звідки
диспетчер знає, який метод викликати на `GET /users/42` і що покласти в його
аргументи?** Відповідь та сама, що й у частині 1 — усе в метаданих, які пишуть
декоратори, а читає рушій (тут — диспетчер).

---

## 2. Механізм: декоратор оголошує, диспетчер виконує

```
   @Controller('users')  →  CONTROLLER_PREFIX_KEY = '/users'   (на класі)
   @Get(':id')           →  ROUTES_KEY += {method:'GET', path:'/:id', handler:'getOne'}
   @Param('id') (idx 0)  →  PARAMS_KEY['getOne'] = { 0: {source:'param', name:'id'} }
                                   │
                                   ▼   (Router.register читає все це)
   CompiledRoute { method:'GET', fullPath:'/users/:id', params:{0:…}, paramTypes:[String] }
                                   │
                                   ▼   (Dispatcher на кожен запит)
   match('GET','/users/42') → pathParams {id:'42'}
   args[0] = pathParams['id']                          // за мапою params
   controller = container.resolve(UserController)       // контейнер частини 1
   return controller.getOne(...args)                    // → JSON
```

Три групи декораторів пишуть **три незалежні шматки метаданих на конструктор
класу**, а диспетчер збирає їх докупи вже під час запиту. Жодного захардкодженого
списку шляхів немає — таблиця маршрутів народжується з декораторів.

## 4. Ключові рішення і чому саме так

### 4.1. `@Controller` неявно вмикає `@Injectable`
Контролеру потрібні сервіси через конструктор, а створює його **контейнер із
частини 1**. Контейнер відмовляється резолвити клас без прапорця `INJECTABLE_KEY`.
Тому `@Controller` ставить цей прапорець сам (як і робить Nest: контролер — це
теж провайдер). Побічно наявність декоратора змушує `tsc` записати
`design:paramtypes` конструктора — без цього контейнер не побачив би залежностей.

### 4.2. Параметр-декоратор пише мапу, а не читає дані
Найважливіша ідея частини (детально — в README, розділ «як параметр-декоратор
знає…»). `parameterIndex` — це ключ. Декоратор складає на класі
`{ [method]: { [index]: {source, name} } }`, а масив аргументів будує диспетчер під
час виклику, ідучи **за індексами**. Це те саме відкладене читання, що й у
контейнера: метадані — оголошення наміру, значення — потім.

### 4.3. Порядок декораторів — і чому ми на нього не покладаємось
Рушій виконує їх знизу вгору: спершу параметр-декоратори методу, потім декоратор
методу, наостанок — декоратор класу. Можна було б на це покластися, але крихко.
Натомість усі три пишуть **незалежні** ключі метаданих на конструктор, а
`Router.register` читає їх **усі разом** — уже після того, як клас повністю
визначено. Тому фактичний порядок не впливає на результат; окремий тест
(`router.test.ts`) фіксує, що мапа параметрів зібрана правильно.

### 4.4. Диспетчер поверх «голого» `node:http`
За умовою — жодного express/fastify. Життєвий цикл запиту в `dispatcher.ts`:
1. `new URL(req.url, base)` — розбір шляху і query;
2. `router.match(method, pathname)` — пошук маршруту (інакше `404`);
3. тіло читаємо **лише** якщо метод має `@Body()`: збираємо чанки з `req.on('data')`,
   `JSON.parse` у `req.on('end')` — той самий код, що на Лекції 3; битий JSON → `400`.
   При цьому **рахуємо накопичені байти**: за перевищенням `maxBodyBytes` (типово
   1 MiB) зупиняємо потік і повертаємо `413` — інакше великий чи нескінченний POST
   роздув би памʼять процесу;
4. будуємо аргументи за мапою параметрів; `@Body` проходить через `ValidationPipe`;
5. `container.resolve(Controller)` і виклик методу;
6. серіалізація: `POST` → `201`, решта → `200`; обробник може повернути
   `HttpResponse(status, body)`, щоб задати статус явно (напр. `404` на «немає юзера»).

Усі винятки ловляться в одну точку (`handle`), щоб жоден не «прорвався» повз
відповідь: `ValidationError` → `400`, `SyntaxError` (битий JSON) → `400`,
`PayloadTooLargeError` (тіло понад ліміт) → `413`, решта → `500`. Важлива деталь
обриву: ліміт **не** знищує сокет одразу (`413`-відповідь не встигла б піти) —
спершу `req.pause()`, потім диспетчер надсилає `413` і аж тоді `req.destroy()`
доривае недочитане завантаження.

### 4.5. Валідація: `plainToInstance` **перед** `validate`
Найтиповіша пастка `class-validator`: він перевіряє **екземпляри класів**, а не
plain-обʼєкти. Сире тіло після `JSON.parse` — plain-обʼєкт, на ньому декоратори
`@IsEmail()` мовчки не спрацюють. Тому `ValidationPipe` робить жорстко по порядку:
`plainToInstance(Dto, body)` → `validate(instance)`. Клас DTO для `@Body()` беремо
з `design:paramtypes` **методу** (за індексом параметра) — той самий рефлекшн, що
й у контейнера, але на рівні методу, а не конструктора.

Наслідки, які прямо покривають acceptance:
- **невалідне** тіло → `ValidationError` зі списком `[{ field, constraints }]` (усі
  порушені поля, а не «перше»), диспетчер віддає його як `400`;
- **валідне** тіло → повертаємо `instance`, тож у метод приходить
  `body instanceof CreateUserDto === true`, а не сирий обʼєкт.

### 4.6. Матчинг маршрутів — посегментно, за специфічністю
`Router` розбиває шлях на сегменти. Літеральний сегмент має збігтися точно, а
`:name` — «джокер», що захоплює будь-яке значення у `pathParams[name]`. Порівнюємо
за кількістю сегментів і поелементно — прозоро й достатньо для ДЗ (query у матчинг
не входить: його окремо парсить `URL`).

**Важлива пастка (і як її закрито):** якщо просто брати *перший* збіг у порядку
реєстрації, то `@Get(':id')`, оголошений раніше за `@Get('me')`, перехопить
`/users/me` — `:id` захопить `"me"`, і `me()` стане мертвим. Тому після реєстрації
`Router` **сортує таблицю за специфічністю** (`bySpecificity`): сегменти зважуються
зліва направо, і на першому, де маршрути різняться, літерал специфічніший за
`:param`. Отже `/users/me` завжди йде в літеральний обробник, а `/users/42` — у
`:id`, **незалежно від порядку декораторів**. Стабільне сортування Node зберігає
порядок реєстрації для маршрутів однакової специфічності. Зафіксовано тестом
«специфічний маршрут виграє в :param…» у `router.test.ts`.

### 4.7. Виклик обробника — через ланцюжок, а не «в лоб» (seam для ДЗ#8)
Наївно було б викликати `controller[method](...args)` одним рядком у `#dispatch`.
Але наступна лекція (ДЗ#8) додає **guards / interceptors / filters** — а це саме
логіка *навколо* виклику обробника. Якщо точка виклику «гола», кожна з цих речей
змусила б переписувати `#dispatch`. Тому виклик загорнуто в **onion-ланцюжок**
(`#runChain`), як interceptor-ланцюг у Nest:

- термінальна ланка — власне виклик методу контролера;
- `reduceRight` обгортає її зареєстрованими ланками; зовнішня бачить `next`, що
  веде до наступної і врешті — до обробника (порядок реєстрації = зовні→всередину);
- **порожній ланцюжок дає рівно `terminal()`** — тобто поточну поведінку «виклик
  як є», без накладних. Тому 24 наявні тести не змінилися.

Що це відкриває для ДЗ#8 без правок `#dispatch`:
- **interceptor** — ланка викликає `next()` і трансформує результат (тест
  «ланцюжок обгортає виклик обробника»);
- **guard** — ланка **не** викликає `next()`, а повертає `HttpResponse(403, …)` →
  обробник не запускається (тест «ланка може відхилити запит…»);
- **filter** — ляже як зовнішня ланка з `try/catch` навколо `next()`.

Ланки отримують `ExecutionContext` (маршрут, `container` для DI, мутабельні
`args`), тож майбутні guards/interceptors резолвляться з того самого контейнера
частини 1. Реєстрація — `dispatcher.use(...)`.

### 4.8. Тести — вбудований `fetch`, без supertest
Дозволені і supertest, і `fetch`. Обрали `fetch`, бо він у Node вбудований — нуль
зайвих залежностей. Хелпер `withServer` піднімає диспетчер на випадковому порту
(`listen(0)`), робить справжній HTTP-запит і закриває сервер. Перевірку
`body instanceof CreateUserDto` робимо **в процесі** (пробний контролер ловить те,
що реально дійшло до обробника) — через мережу `instanceof` не переживе JSON.

## 5. Як рішення лягають на acceptance criteria

| Критерій | Де це в коді/тестах |
| --- | --- |
| Фреймворків немає | `grep -RE "@nestjs|express|fastify" package.json src/` — порожньо |
| Маршрути з декораторів | `router.ts`: `Reflect.getMetadata('design:paramtypes', …)`; таблиця з `ROUTES_KEY` |
| Префікс склеюється | тест `GET /users/1` → `200`; `router.test.ts`: `fullPath === '/users/:id'` |
| `@Param` працює | тест `GET /users/42`, id доходить до методу і формує відповідь |
| `@Query` працює | тест `GET /users?limit=1` → лишається 1 елемент |
| `@Body` працює | тест `POST /users` валідний → `201` з розпарсеним тілом |
| Валідація відхиляє | тест `POST {email:'not-an-email'}` → `400`, тіло матчить `/email/` |
| Валідація пропускає | тест `received instanceof CreateUserDto` через диспетчер |
| Контейнер задіяно | тест `controller.users === container.resolve(UserService)` (той самий singleton) |
| Тести проходять | `npm test` → 21 passed, exit 0 |
| Docker | `docker compose run --rm api npm test` → 21 passed, exit 0 |

## 7. Головний висновок

Після частини 2 «магія» контролерів Nest розкладається на ті самі дві дії, що й у
частині 1: **декоратор пише метадані** (префікс, маршрут, `index → джерело`,
правила DTO), а **рушій їх читає** — тільки читач тепер не контейнер, а диспетчер,
який на кожному HTTP-запиті збирає аргументи за метаданими й кличе метод через той
самий контейнер. Ніякого прихованого рушія: увесь шлях від `GET /users/42` до
виклику `getOne('42')` видно в `router.ts` і `dispatcher.ts`.
